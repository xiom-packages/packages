# Bindings-lane compiler findings (xiom-packages bindings lane)

Findings collected while building the FFI/binding packages (`xiom.sqlite`
pilot) on the pinned toolchain, with runnable reductions in
`docs/repro/bindings-pilot/`.

This is the **bindings-lane delta**, mirroring the PULSE-lane practice. The
packages coordinator folds entries into `docs/COMPILER-FINDINGS.md` (shared
file, native lane); this file is the lane-owned detail with repros and exact
workarounds so the compiler lane can bisect without re-deriving context.
Nothing here is a gate.

Status legend: **OPEN** = no fix known in the pin; **WORKED-AROUND** = package
avoids the shape; **MERGED** = recorded in the shared findings doc.

| B-02 | OPEN (v0.64.0), MERGED (native 95227e16) | **References to exported `pub const`s inside confined (`unsafe`) blocks, and long const-comparison chains, recurse the resolver to a stack overflow** (`thread '<unknown>' has overflowed its stack`, exit `-1073741571`). No standalone file reproduced it (small catalogs are green), so the package is the reproducer | `src/ffi.xi` uses numeric literals inside confined functions and a literal-based `error_name`; the exported `SQLITE_*` consts are unchanged for callers. | B-03 | OPEN (v0.64.0), MERGED (native 95227e16), **minimal shape green v0.64.2** | **Cross-module const aliases recurse the resolver**: `pub const A: Int = other_module.B;` in a facade module crashed when a consumer referenced `A` (a literal-valued const in the same position is fine) | Regression pair while building `xiom.sqlite` 0.2.0: facade consts as aliases -> stack overflow in the suite build; facade consts as literals -> green. | B-04 | OPEN (documented 2026-10-02/03 in shared findings), **minimal shape green v0.64.2** | **A module cannot import its parent** (`use parent;` from a child silently fails to resolve the parent's functions) | Re-hit in `xiom.sqlite`: `rows.xi`/`migration.xi` could not `use xiom.sqlite;`; sibling layout (`xiom.sqlite.ffi`) + qualified calls fixed it. The shared doc's 2026-10-03 re-test reframes the boundary as `pub` visibility for call shapes; our failing shape was a child->parent *import* with pub functions, so both notes apply; **minimal shape on v0.64.2 (2026-10-09): GREEN (`child-import-parent/pkg/`, value=42); the sibling-layout guidance stays for the original catalog** | flat sibling layout: FFI core is `xiom.sqlite.ffi`, only the parent facade imports children; siblings call each other with a qualified prefix (`ffi.prepare(...)`) | structural; forces a sibling split per package |
| B-05 | OPEN (v0.64.0), MERGED (native 95227e16) | **`xiom.ffi.alloc` inside a confined block + `xiom.ffi.free` spins the guard heap.** The guard pass rewrites the inlined `alloc` call to `xiom_guard_alloc` inside the block while `free` still reaches libc; the guard heap then loops forever (flat memory, ~100% CPU, no output). Before diagnosis this ran ~21 minutes and is the most plausible contributor to a machine memory spike/restart on 2026-10-08 | `docs/repro/bindings-pilot/alloc-guard-spin/` (runnable; never run without a watchdog): watchdog kill at 8 s, 8.1 CPU-s burned, flat 4.5 MB RSS. Controls that exit 0: same code without `ffi.free`, or module-local `extern "C" { fn malloc/free }` used as a pair | no malloc/free in confined blocks. C out-params (`sqlite3_open`, `sqlite3_prepare_v2`) write into an XIOM-owned 8-byte `Vec[UInt8]` slot read back byte-wise | hard hang; watchdog mandatory for any suite that touches ffi allocation. Fix options: guard-aware `free`, or refuse/redirect libc `free` of guard pointers. **RE-TESTED on v0.64.1 (2026-10-08): STILL OPEN -- identical spin (8 s watchdog, flat 4.5 MB)**; **RE-TESTED on v0.64.2 (2026-10-09): STILL OPEN -- identical spin (10 s watchdog, 8.7 CPU-s, flat 4.5 MB); runtime-side fix still pending; native v0.64.2 re-test: 6.9 CPU-s / 8 s, flat 4.5 MB** |
| B-06 | OPEN (v0.64.0), MERGED (native 95227e16), **FIXED v0.64.1** | **A module exporting associated fns whose last segment is `up`/`down` crashed the full package catalog when the suite imports `xiom.test`** (compiler stack overflow, exit `-1073741571`, no output). Context-dependent: two standalone reductions of the shape compile green on v0.64.0 | Bisect transcript (`BINDINGS-SESSION.md`): with the full pre-fix `xiom.sqlite` catalog, removing `MigrationManager.up` removed the crash; renaming a probe variant back to `up` reintroduced it; renaming to `migrate_up`/`migrate_down` made the package green (16/16 x6). **RE-TESTED on v0.64.1 (2026-10-08): FIXED -- a scratch copy of `xiom.sqlite` with `MigrationManager.up`/`down` restored builds and runs 16/16 green through the suite**; **RE-TESTED on v0.64.2 (2026-10-09): still green (`up=1 down=1`); native re-verified** | migration methods renamed `migrate_up`/`migrate_down` (may be restored at the next pin if desired; not a drive-by refactor) | compile-time crash on v0.64.0; resolved on v0.64.1 |
| B-07 | OPEN (v0.64.0), **STILL OPEN v0.64.2** | **Unqualified names from a stdlib import are unresolved in a module whose own path ends with the same alias**: a module named `xiom.sqlite.ffi` cannot `use xiom.ffi;` and call `ptr_read_u64_le(...)` (the alias `ffi` shadows/self-collides). Relatedly, unqualified calls to parent-module functions fail (B-04); qualified forms (`ffi.prepare`) work | `xiom.sqlite` pre-fix `src/ffi.xi` build log: `undefined variable 'ptr_read_u64_le'` with `use xiom.ffi;` present; compiled once the stdlib import was dropped (byte-wise reads from the XIOM buffer instead); **minimal shape on v0.64.2 (2026-10-09): STILL BROKEN (`ffi-alias-shadow/probe.xi`: `module probe.ffi` + `use xiom.ffi;` -> `undefined variable 'c_strlen'`)** | avoid importing a stdlib module whose alias equals the module's own last segment; use an explicitly different module name or read through XIOM-owned memory | compile-time only; confusing (the import line looks legal) |
| B-08 | OPEN (v0.64.0 tooling), MERGED (native 95227e16), **FIXED v0.64.2** | **`xiom --run` masks the program's exit code**: a suite whose `main` returned 5 finished with `xiom --run` exit 0 | `xiom.sqlite` suite runs on 2026-10-08: `[FAIL]` x5 + returning 5 -> `$LASTEXITCODE` 0 in every failing run; `port.ps1`'s `[PASS]`/`[FAIL]` marker counting is the reliable signal. **RE-TESTED on v0.64.1 (2026-10-08): STILL OPEN -- `main(){return 5}` still exits 0 under `--run`**; **RE-TESTED on v0.64.2 (2026-10-09): FIXED -- compiler prints `exit code: 5` and exits 5 (m228); probe committed at `docs/repro/bindings-pilot/run-exit/`; native probe 5 -> exit 5** | `port.ps1` counts markers (already the case); probes must check printed output, not exit codes | masked suite failures anywhere callers trust `--run`'s status |
| B-09 | OPEN (v0.64.0), **FIXED v0.64.1** | **A large confined `unsafe` block that creates a Win32 window + WGL context poisons the whole binary**: builds exit `-1073740791` (0xC0000409) with **no output at all** -- the crash is before the first `io.println`, i.e. a build/codegen property, deterministic across rebuilds (3/3 checked). | B-10 | OPEN (v0.64.1), **STILL OPEN v0.64.2** | **A local fn-pointer variable named `alloc` is silently redirected to the guard allocator inside confined blocks.** `let alloc = ptr as fn(Int, Int, *UInt8) -> Int32;` then `alloc(1, 0, &out)` inside `unsafe` calls `xiom_guard_alloc` instead of the intended foreign function: the call returns success but the out-param is never written (observed with ODBC's `SQLAllocHandle` -> env handle stayed 0, every later call returned `SQL_INVALID_HANDLE`). Same rewrite family as B-05 (`malloc`->`xiom_guard_alloc` in confined blocks); the pass appears to key on the callee NAME, not the callee symbol | `xiom.odbc` 0.2.0: minimal repro delta is the variable name -- `let alloc = ...; alloc(...)` fails, `let f_alloc = ...; f_alloc(...)` works (handle valid). Compiler lane: exclude non-builtin locals from the guard rewrite |

## Notes for the compiler lane

- **v0.64.2 re-test sweep (2026-10-09, v0.64.2)**: all **19**
  binding suites green x1 through `port.ps1` (counts in the
  `BINDINGS-SESSION.md` relay); **B-01 FIXED** (6/6 enum-payload rebuilds
  all-true; m231) and **B-08 FIXED** (a program returning 5 now prints
  `exit code: 5` and the compiler exits 5; m228; new repro
  `docs/repro/bindings-pilot/run-exit/`); B-06/B-09 still fixed; **B-05
  STILL OPEN** (spin reproduced: 10 s watchdog, 8.7 CPU-s, flat 4.5 MB --
  runtime side) and **B-10 STILL OPEN** (odbc 3-way scratch control:
  `f_alloc` 5/5 + `my_alloc` 5/5 green, `alloc` FAIL). B-02 was not
  re-tested (no live trigger); the B-03/B-04 minimal shapes are GREEN on
  v0.64.2 (`const-alias/`, `child-import-parent/`) and B-07's minimal shape
  is STILL BROKEN (`ffi-alias-shadow/`). The sqlite enum
  workaround is RETIRED (`xiom.sqlite` 0.3.0 restores the enum model: 16/16
  x6 fresh build cycles + pin matrix x1 on v0.64.2; the publish is the native
  lane's call); the B-05/B-10 workarounds stay in force.
- **v0.64.1 re-test sweep (2026-10-08)**: B-06 FIXED, B-09 FIXED; B-01
  (enum payload ND) STILL OPEN with the same signature, B-05 (alloc/free
  guard spin) STILL OPEN, B-08 (`--run` exit masking) STILL OPEN. B-02/B-03
  (const resolver recursion) and B-04/B-07 (import/member-name resolution)
  were not re-tested: their triggers need the large pre-fix catalogs that no
  longer exist in the tree; rebuild them from this doc's descriptions if
  needed. The enum workaround in `xiom.sqlite` (`SPEC.md` §5) and the
  alloc/free avoidance stay in force.
- **B-10 discovered after the sweep (v0.64.1)**: the `alloc`-name rewrite in
  confined blocks is new evidence for the B-05 family; the guard pass should
  only rewrite calls that resolve to the actual stdlib allocator, not local
  fn-pointer variables with the same name.
- B-01, B-02, B-06 may share one root cause family (nondeterministic
  layout/name-resolution recursion under catalog build). The strongest
  runnable artifact is B-01's `pkg/` (reproduces in ~1/3 of rebuilds and is
  open on both v0.64.0 and v0.64.1); B-05 remains a clean, deterministic
  reproducer (watchdog required).
- All probes were built with `--c-source <abs>\vendor\sqlite3.c` where the
  real FFI is involved; the amalgamation itself is never edited.
- The bindings lane re-tests these at the next pin; `SPEC.md` §5 and the
  session ledger record which workarounds can be dropped once fixed.
