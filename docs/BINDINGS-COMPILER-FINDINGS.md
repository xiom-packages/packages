# Bindings-lane compiler findings (xiom-packages bindings lane)

Findings collected while building the FFI/binding packages (`xiom.sqlite`
pilot) on the pinned toolchain, with runnable reductions in
`docs/repro/bindings-pilot/`.

This is the **bindings-lane delta**, mirroring the PULSE-lane practice. The
packages coordinator folds entries into `docs/COMPILER-FINDINGS.md` (shared
file, native lane); this file is the lane-owned detail with repros and exact
workarounds so the compiler lane can bisect without re-deriving context.
Nothing here is a gate.

Status legend: **OPEN** = no fix known in the pin; **WORKED-AROUND** = package
avoids the shape; **MERGED** = recorded in the shared findings doc.

| B-01 | OPEN (v0.64.0), MERGED (native 95227e16) | **User-enum payload reads are nondeterministically miscompiled across rebuilds.** A struct wrapping an enum with payloads (`Integer(Int)`, `Text(Str)`, ...) + match-based accessors: some builds read every payload wrong (accessors return `None`/wrong values), other builds are green; the same binary is self-consistent. In the pre-fix `xiom.sqlite` suite the run alternated 16/16 and 11/16 PASS across 6 consecutive rebuilds; a 4-check micro probe flipped all-false in 1 of 6 builds | `docs/repro/bindings-pilot/enum-payload-nd/pkg/` (enum model + real FFI + rows): 2 of 6 rebuilds printed `B=false` on 2026-10-08; `probe.xi` (single file) retains the shape. Same class as the `xiom.graphql` enum-payload finding in `docs/COMPILER-FINDINGS.md` | `xiom.sqlite` 0.2.0 uses a tagged struct (`kind: Int` + payload fields) instead of an enum; 8/8 micro and 6/6 suite rebuilds green after the change. `SPEC.md` §5 records the model as a portability workaround to re-test at the next pin | silent wrong results with no diagnostic; any package exposing enum payloads is affected probabilistically. Needs a compiler-lane bisect (what makes a build "bad"?). |
| B-02 | OPEN (v0.64.0), MERGED (native 95227e16) | **References to exported `pub const`s inside confined (`unsafe`) blocks, and long const-comparison chains, recurse the resolver to a stack overflow** (`thread '<unknown>' has overflowed its stack`, exit `-1073741571`). Full-catalog builds only: standalone reductions compile green | Pre-fix `xiom.sqlite` `src/ffi.xi`: `open()` compared `rc != SQLITE_OK` and built `SqliteError.new(SQLITE_ERROR, ...)` inside its confined block; deleting the error branches or replacing the consts with literals made it compile. `error_name` with 30+ const arms crashed its callers until rewritten with literals. No standalone file reproduced it (small catalogs are green), so the package is the reproducer | `src/ffi.xi` uses numeric literals inside confined functions and a literal-based `error_name`; the exported `SQLITE_*` consts are unchanged for callers. A facade with `pub const X = other.X` aliases also recursed -- facade consts are literals (B-03) | compile-time crash; costs resolver bisects because small probes pass |
| B-03 | OPEN (v0.64.0), MERGED (native 95227e16) | **Cross-module const aliases recurse the resolver**: `pub const A: Int = other_module.B;` in a facade module crashed when a consumer referenced `A` (a literal-valued const in the same position is fine) | Regression pair while building `xiom.sqlite` 0.2.0: facade consts as aliases -> stack overflow in the suite build; facade consts as literals -> green. Transcript in `BINDINGS-SESSION.md` (session ledger) | all facade consts use literal values, duplicated with a "keep in sync with ffi" comment; tests pin the codes the FFI actually returns | compile-time crash; blocks the common "re-export the constants" facade idiom |
| B-04 | OPEN (documented 2026-10-02/03 in shared findings) | **A module cannot import its parent** (`use parent;` from a child silently fails to resolve the parent's functions) | Re-hit in `xiom.sqlite`: `rows.xi`/`migration.xi` could not `use xiom.sqlite;`; sibling layout (`xiom.sqlite.ffi`) + qualified calls fixed it. The shared doc's 2026-10-03 re-test reframes the boundary as `pub` visibility for call shapes; our failing shape was a child->parent *import* with pub functions, so both notes apply | flat sibling layout: FFI core is `xiom.sqlite.ffi`, only the parent facade imports children; siblings call each other with a qualified prefix (`ffi.prepare(...)`) | structural; forces a sibling split per package |
| B-05 | OPEN (v0.64.0), MERGED (native 95227e16) | **`xiom.ffi.alloc` inside a confined block + `xiom.ffi.free` spins the guard heap.** The guard pass rewrites the inlined `alloc` call to `xiom_guard_alloc` inside the block while `free` still reaches libc; the guard heap then loops forever (flat memory, ~100% CPU, no output). Before diagnosis this ran ~21 minutes and is the most plausible contributor to a machine memory spike/restart on 2026-10-08 | `docs/repro/bindings-pilot/alloc-guard-spin/` (runnable; never run without a watchdog): watchdog kill at 8 s, 8.1 CPU-s burned, flat 4.5 MB RSS. Controls that exit 0: same code without `ffi.free`, or module-local `extern "C" { fn malloc/free }` used as a pair | no malloc/free in confined blocks. C out-params (`sqlite3_open`, `sqlite3_prepare_v2`) write into an XIOM-owned 8-byte `Vec[UInt8]` slot read back byte-wise | hard hang; watchdog mandatory for any suite that touches ffi allocation. Fix options: guard-aware `free`, or refuse/redirect libc `free` of guard pointers |
| B-06 | OPEN (v0.64.0), MERGED (native 95227e16) | **A module exporting associated fns whose last segment is `up`/`down` crashed the full package catalog when the suite imports `xiom.test`** (compiler stack overflow, exit `-1073741571`, no output). Context-dependent: two standalone reductions of the shape compile green on v0.64.0 | Bisect transcript (`BINDINGS-SESSION.md`): with the full pre-fix `xiom.sqlite` catalog, removing `MigrationManager.up` removed the crash; renaming a probe variant back to `up` reintroduced it; renaming to `migrate_up`/`migrate_down` made the package green (16/16 x6). Reductions attempted green: `docs/repro/bindings-pilot/up-down-name/` (bare `T.up` and the faithful migration reduction) | migration methods renamed `migrate_up`/`migrate_down`; wrapper fns updated | compile-time crash; likely the same resolver-recursion class as B-02 -- compiler lane can bisect with the pre-fix full catalog |
| B-07 | OPEN (v0.64.0) | **Unqualified names from a stdlib import are unresolved in a module whose own path ends with the same alias**: a module named `xiom.sqlite.ffi` cannot `use xiom.ffi;` and call `ptr_read_u64_le(...)` (the alias `ffi` shadows/self-collides). Relatedly, unqualified calls to parent-module functions fail (B-04); qualified forms (`ffi.prepare`) work | `xiom.sqlite` pre-fix `src/ffi.xi` build log: `undefined variable 'ptr_read_u64_le'` with `use xiom.ffi;` present; compiled once the stdlib import was dropped (byte-wise reads from the XIOM buffer instead) | avoid importing a stdlib module whose alias equals the module's own last segment; use an explicitly different module name or read through XIOM-owned memory | compile-time only; confusing (the import line looks legal) |
| B-08 | OPEN (v0.64.0 tooling), MERGED (native 95227e16) | **`xiom --run` masks the program's exit code**: a suite whose `main` returned 5 finished with `xiom --run` exit 0 | `xiom.sqlite` suite runs on 2026-10-08: `[FAIL]` x5 + returning 5 -> `$LASTEXITCODE` 0 in every failing run; `port.ps1`'s `[PASS]`/`[FAIL]` marker counting is the reliable signal | `port.ps1` counts markers (already the case); probes must check printed output, not exit codes | masked suite failures anywhere callers trust `--run`'s status |
| B-09 | OPEN (v0.64.0) | **A large confined `unsafe` block that creates a Win32 window + WGL context poisons the whole binary**: builds exit `-1073740791` (0xC0000409) with **no output at all** -- the crash is before the first `io.println`, i.e. a build/codegen property, deterministic across rebuilds (3/3 checked). Isolated sub-parts are green: a window+`GetDC`+cleanup function with the same 12-argument fn-pointer cast runs, and dl-load/contextless versions run; folding `ChoosePixelFormat`/`SetPixelFormat`/`wglCreateContext`/`wglMakeCurrent`/string-query into the same function makes every build crash | runnable repro + control: `docs/repro/bindings-pilot/win32-gl-unsafe/` (`probe_q2.xi` crashes 3/3 rebuilds, no output; `probe_q1.xi` control green). Found building the pre-fix `xiom.opengl` probe (pure-XIOM Win32 path) | `xiom.opengl` 0.2.0 moved the staged probe into the vendored C bridge `src/gl_probe.c` (`--c-source`, no `--link`); the XIOM side is ten one-line `extern` wrappers over safe functions | build-shaped pre-output crash; not attributable to a single source line; the bounded q1/q2 pair isolates the trigger to the added WGL stage |

## Notes for the compiler lane

- B-01, B-02, B-06 may share one root cause family (nondeterministic
  layout/name-resolution recursion under catalog build). The strongest
  runnable artifact is B-01's `pkg/` (reproduces in ~1/3 of rebuilds);
  B-05 and B-09 are clean, deterministic reproducers (watchdog for B-05;
  B-09 fails fast before output).
- All probes were built with `--c-source <abs>\vendor\sqlite3.c` where the
  real FFI is involved; the amalgamation itself is never edited.
- The bindings lane re-tests these at the next pin; `SPEC.md` §5 and the
  session ledger record which workarounds can be dropped once fixed.
