# Bindings-lane compiler findings (xiom-packages bindings lane)

Findings collected while building the FFI/binding packages (`xiom.sqlite`
pilot) on the pinned toolchain, with runnable reductions in
`docs/repro/bindings-pilot/`.

This is the **bindings-lane delta**, mirroring the PULSE-lane practice. The
packages coordinator folds entries into `docs/COMPILER-FINDINGS.md` (shared
file, native lane); this file is the lane-owned detail with repros and exact
workarounds so the compiler lane can bisect without re-deriving context.
Nothing here is a gate.

Status legend: **OPEN** = no fix known in the pin; **WORKED-AROUND** = package
avoids the shape; **MERGED** = recorded in the shared findings doc.

Same class as the `xiom.graphql` enum-payload finding in `docs/COMPILER-FINDINGS.md` | `xiom.sqlite` 0.2.0 uses a tagged struct (`kind: Int` + payload fields) instead of an enum; 8/8 micro and 6/6 suite rebuilds green after the change. `SPEC.md` §5 records the model as a portability workaround to re-test at the next pin | silent wrong results with no diagnostic; any package exposing enum payloads is affected probabilistically. Needs a compiler-lane bisect (what makes a build "bad"?). **RE-TESTED on v0.64.1 (2026-10-08): STILL OPEN -- same signature, 2/6 builds fail (`B=false`)**. **FIXED on v0.64.2 (m231; native 2026-10-09): 3/3 rebuilds `A=B=C=D=true`; the enum-rebuild workarounds can be dropped at the next touches.** |
| B-02 | OPEN (v0.64.0), MERGED (native 95227e16) | **References to exported `pub const`s inside confined (`unsafe`) blocks, and long const-comparison chains, recurse the resolver to a stack overflow** (`thread '<unknown>' has overflowed its stack`, exit `-1073741571`). Full-catalog builds only: standalone reductions compile green | Pre-fix `xiom.sqlite` `src/ffi.xi`: `open()` compared `rc != SQLITE_OK` and built `SqliteError.new(SQLITE_ERROR, ...)` inside its confined block; deleting the error branches or replacing the consts with literals made it compile. `error_name` with 30+ const arms crashed its callers until rewritten with literals. No standalone file reproduced it (small catalogs are green), so the package is the reproducer | `src/ffi.xi` uses numeric literals inside confined functions and a literal-based `error_name`; the exported `SQLITE_*` consts are unchanged for callers. | B-03 | OPEN (v0.64.0), MERGED (native 95227e16) | **Cross-module const aliases recurse the resolver**: `pub const A: Int = other_module.B;` in a facade module crashed when a consumer referenced `A` (a literal-valued const in the same position is fine) | Regression pair while building `xiom.sqlite` 0.2.0: facade consts as aliases -> stack overflow in the suite build; facade consts as literals -> green. | B-04 | OPEN (documented 2026-10-02/03 in shared findings) | **A module cannot import its parent** (`use parent;` from a child silently fails to resolve the parent's functions) | Re-hit in `xiom.sqlite`: `rows.xi`/`migration.xi` could not `use xiom.sqlite;`; sibling layout (`xiom.sqlite.ffi`) + qualified calls fixed it. The shared doc's 2026-10-03 re-test reframes the boundary as `pub` visibility for call shapes; our failing shape was a child->parent *import* with pub functions, so both notes apply | flat sibling layout: FFI core is `xiom.sqlite.ffi`, only the parent facade imports children; siblings call each other with a qualified prefix (`ffi.prepare(...)`) | structural; forces a sibling split per package |
| B-05 | OPEN (v0.64.0), MERGED (native 95227e16) | **`xiom.ffi.alloc` inside a confined block + `xiom.ffi.free` spins the guard heap.** The guard pass rewrites the inlined `alloc` call to `xiom_guard_alloc` inside the block while `free` still reaches libc; the guard heap then loops forever (flat memory, ~100% CPU, no output). Before diagnosis this ran ~21 minutes and is the most plausible contributor to a machine memory spike/restart on 2026-10-08 | `docs/repro/bindings-pilot/alloc-guard-spin/` (runnable; never run without a watchdog): watchdog kill at 8 s, 8.1 CPU-s burned, flat 4.5 MB RSS. Controls that exit 0: same code without `ffi.free`, or module-local `extern "C" { fn malloc/free }` used as a pair | no malloc/free in confined blocks. C out-params (`sqlite3_open`, `sqlite3_prepare_v2`) write into an XIOM-owned 8-byte `Vec[UInt8]` slot read back byte-wise | hard hang; watchdog mandatory for any suite that touches ffi allocation. Fix options: guard-aware `free`, or refuse/redirect libc `free` of guard pointers. **RE-TESTED on v0.64.1 (2026-10-08): STILL OPEN -- identical spin (8 s watchdog, flat 4.5 MB)**. **RE-TESTED on v0.64.2 (native 2026-10-09): STILL OPEN -- identical spin (6.9 CPU-s / 8 s, flat 4.5 MB).** |
| B-06 | OPEN (v0.64.0), MERGED (native 95227e16), **FIXED v0.64.1** | **A module exporting associated fns whose last segment is `up`/`down` crashed the full package catalog when the suite imports `xiom.test`** (compiler stack overflow, exit `-1073741571`, no output). Context-dependent: two standalone reductions of the shape compile green on v0.64.0 | Bisect transcript (`BINDINGS-SESSION.md`): with the full pre-fix `xiom.sqlite` catalog, removing `MigrationManager.up` removed the crash; renaming a probe variant back to `up` reintroduced it; renaming to `migrate_up`/`migrate_down` made the package green (16/16 x6). **RE-TESTED on v0.64.1 (2026-10-08): FIXED -- a scratch copy of `xiom.sqlite` with `MigrationManager.up`/`down` restored builds and runs 16/16 green through the suite** | migration methods renamed `migrate_up`/`migrate_down` (may be restored at the next pin if desired; not a drive-by refactor) | compile-time crash on v0.64.0; resolved on v0.64.1. **Re-verified v0.64.2 (native 2026-10-09): up/down probe `up=1 down=1`.** |
| B-07 | OPEN (v0.64.0) | **Unqualified names from a stdlib import are unresolved in a module whose own path ends with the same alias**: a module named `xiom.sqlite.ffi` cannot `use xiom.ffi;` and call `ptr_read_u64_le(...)` (the alias `ffi` shadows/self-collides). | B-08 | OPEN (v0.64.0 tooling), MERGED (native 95227e16) | **`xiom --run` masks the program's exit code**: a suite whose `main` returned 5 finished with `xiom --run` exit 0 | `xiom.sqlite` suite runs on 2026-10-08: `[FAIL]` x5 + returning 5 -> `$LASTEXITCODE` 0 in every failing run; `port.ps1`'s `[PASS]`/`[FAIL]` marker counting is the reliable signal. **RE-TESTED on v0.64.1 (2026-10-08): STILL OPEN -- `main(){return 5}` still exits 0 under `--run`** | `port.ps1` counts markers (already the case); probes must check printed output, not exit codes | masked suite failures anywhere callers trust `--run`'s status. **FIXED on v0.64.2 (m228; native 2026-10-09): `--run` returned the program's exit code (probe returns 5 -> exit 5).** |
| B-09 | OPEN (v0.64.0), **FIXED v0.64.1** | **A large confined `unsafe` block that creates a Win32 window + WGL context poisons the whole binary**: builds exit `-1073740791` (0xC0000409) with **no output at all** -- the crash is before the first `io.println`, i.e. a build/codegen property, deterministic across rebuilds (3/3 checked). | B-10 | OPEN (v0.64.1) | **A local fn-pointer variable named `alloc` is silently redirected to the guard allocator inside confined blocks.** `let alloc = ptr as fn(Int, Int, *UInt8) -> Int32;` then `alloc(1, 0, &out)` inside `unsafe` calls `xiom_guard_alloc` instead of the intended foreign function: the call returns success but the out-param is never written (observed with ODBC's `SQLAllocHandle` -> env handle stayed 0, every later call returned `SQL_INVALID_HANDLE`). Same rewrite family as B-05 (`malloc`->`xiom_guard_alloc` in confined blocks); the pass appears to key on the callee NAME, not the callee symbol | `xiom.odbc` 0.2.0: minimal repro delta is the variable name -- `let alloc = ...; alloc(...)` fails, `let f_alloc = ...; f_alloc(...)` works (handle valid). C reference probe outside XIOM verified the API/calling convention was correct all along. `docs/repro/bindings-pilot/` has no dedicated bundle yet; the odbc module + SPEC §3 documents the trigger | name all bridge locals with a prefix (`f_alloc`, `f_setenv`, ...) as a rule; NEVER name a fn-pointer `alloc` | silent wrong dispatch in confined blocks (no diagnostic); any FFI package can hit it. Compiler lane: exclude non-builtin locals from the guard rewrite. **RE-TESTED on v0.64.2 (native 2026-10-09): STILL OPEN -- a scratch `xiom.odbc` copy with the local renamed back to `alloc` FAILS (`probe: failed`, exit 1) where the `f_alloc` control passes 5/5; keep the `f_` prefix.** |

## Notes for the compiler lane

- **v0.64.1 re-test sweep (2026-10-08)**: B-06 FIXED, B-09 FIXED; B-01
  (enum payload ND) STILL OPEN with the same signature, B-05 (alloc/free
  guard spin) STILL OPEN, B-08 (`--run` exit masking) STILL OPEN. B-02/B-03
  (const resolver recursion) and B-04/B-07 (import/member-name resolution)
  were not re-tested: their triggers need the large pre-fix catalogs that no
  longer exist in the tree; rebuild them from this doc's descriptions if
  needed. The enum workaround in `xiom.sqlite` (`SPEC.md` §5) and the
  alloc/free avoidance stay in force.
- **B-10 discovered after the sweep (v0.64.1)**: the `alloc`-name rewrite in
  confined blocks is new evidence for the B-05 family; the guard pass should
  only rewrite calls that resolve to the actual stdlib allocator, not local
  fn-pointer variables with the same name.
- B-01, B-02, B-06 may share one root cause family (nondeterministic
  layout/name-resolution recursion under catalog build). The strongest
  runnable artifact is B-01's `pkg/` (reproduces in ~1/3 of rebuilds and is
  open on both v0.64.0 and v0.64.1); B-05 remains a clean, deterministic
  reproducer (watchdog required).
- All probes were built with `--c-source <abs>\vendor\sqlite3.c` where the
  real FFI is involved; the amalgamation itself is never edited.
- The bindings lane re-tests these at the next pin; `SPEC.md` §5 and the
  session ledger record which workarounds can be dropped once fixed.
