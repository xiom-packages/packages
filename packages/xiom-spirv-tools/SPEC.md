## 2. Surface (what is bound)

The oracle is every function declaration inside the header's `extern "C"`
block whose name starts with `spv`: **67 functions** at this pin.  All 67
are bound as typed wrappers (family-split generated modules, one wrapper
per function, `p_<name>` handle in `StSymbols` + `dl.dl_sym` resolver).
**55** of the 67 are exported by the shipped DLL; the remaining **12** are
documented as a shipping gap in `docs/COVERAGE.md` (name-level resolve
proof in the suite) and their wrappers carry `requires: syms.p_x != 0`.
The gap is **source-verified** (PROVENANCE.md §2): the ten `spvOptimizer*`
functions are defined in `source/opt/optimizer.cpp`, which upstream builds
into the separate `SPIRV-Tools-opt` library target, not the
`SPIRV-Tools-shared` DLL; the two `spvOperandIsConcrete*` helpers are
declared/defined without `SPIRV_TOOLS_EXPORT` by upstream design.

Constants: **222** generated values (11 enums + `kDefaultMaxIdBound`).
Function-like macros (`SPV_BIT`, `SPV_FORCE_16_BIT_ENUM`/`_32_BIT`) are
compile-time helpers, not constants; the enums they feed are bound.

## 3. C / C++ split

`Include\spirv-tools\` ships four headers:

- `libspirv.h` -- the **C API** (`extern "C"`, `spv*`): this is the bound
  surface.
- `libspirv.hpp` -- **C++ API** (`spvtools::Context`, `spvtools::Optimizer`,
  RAII wrappers): exported from the DLL as ~62 mangled MSVC symbols
  (visible in the raw export dump) and deliberately **excluded** from this
  binding -- a C++ ABI is not an FFI surface (compare the glslang
  C++-bridge route in the program plan §2; a bridge is out of scope for
  slice A1).
- `linker.hpp`, `optimizer.hpp` -- header-only C++ helper wrappers over the
  same C API: excluded (no additional exported C surface).

## 4. Safe boundary (G5)

- `unsafe` lives only in the generated family modules (`st_core.xi`,
  `st_validator.xi`, `st_optimizer.xi`, `st_reducer_fuzzer.xi`,
  `st_codec.xi`, `st_operand.xi` -- one confined block per wrapper), in
  `src/st_readout.xi` (the copy-out helpers), and in the generated
  resolver's `dl.dl_sym` calls via `xiom.ffi.dl`.
- Out-params: one owned zeroed `Vec[UInt8]` slot per parameter; byte-indexed
  reads/writes only (`st_slot_read_u64` / `st_slot_write_u64`); no
  `ffi.ptr_write_*`, no pointer arithmetic (B-11/B-16/B-17 discipline).
- C-owned structs (`spv_binary_t`, `spv_text_t`, `spv_diagnostic_t`) are
  copied out through the two-function C bridge (`src/st_probe_bridge.c`)
  into owned slots; XIOM never dereferences a foreign pointer (B-20).
- `Int`-addressed raw data (words/code pointers) is passed as `Int` and the
  `as *UInt8` cast happens on the call expression inside the wrapper's
  confined block: a cast performed in a separate helper does not survive
  (probe evidence recorded in AUDIT.md -- the int-to-ptr cast family).
