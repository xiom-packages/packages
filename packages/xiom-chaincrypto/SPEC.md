# xiom.chaincrypto -- Specification

Status: `incubating` (implemented, conformance-green with compiler v0.62.2;
19/19 checks; not published).
Manifest: `package.xi` (`xiom.chaincrypto`, version `0.1.0`).
Module: `src/chaincrypto.xi` (`module xiom.chaincrypto`).
Depends on `xiom.std`; the library imports `xiom.convert` (tests add
`xiom.test`, `xiom.io`, `xiom.string.compare`). Pure XIOM, no FFI, no I/O.

## 1. Scope

Deterministic commitment and proof **structures** over caller-supplied
opaque integer hashes:

1. an append-only hash-tree accumulator with leaf count, root and root
   history records;
2. membership proofs (sibling list plus direction bits) with verification;
3. an m-of-n threshold approval model with an execution gate and receipts;
4. commit-reveal records with commit/reveal/expiry ticks;
5. duplicate-approval and replay rejection throughout;
6. a pinned error catalog.

## 2. Non-goals

- **No cryptography.** The module never hashes, never generates or verifies
  signatures, and holds no keys. Hash values are caller-supplied `Int`s;
  the internal node mix is opaque structural bookkeeping, not a
  cryptographic compression function.
- No wire serialization or persistence of accumulators, proofs or records.
- No consistency proofs, batch proofs, or multi-accumulator coordination.
- No side-channel hardening; not constant-time.
- No global state, no threads, no I/O.

## 3. Data model

All struct fields are public. Values are immutable by convention: the
functions that "update" (append, approve, execute, reveal, refund) take a
reference and return a **new** value.

```xi
pub type ChainRootRecord = {
  leaf_count: Int;
  root: Int;
}

pub type ChainAccumulator = {
  leaf_count: Int;
  root: Int;
  leaves: Vec[Int];        // leaf hashes, append order
  level_sizes: Vec[Int];   // nodes per level, level 0 = leaves
  level_starts: Vec[Int];  // index into levels of each level's first node
  levels: Vec[Int];        // all levels concatenated
  history_counts: Vec[Int];// leaf count after append i+1
  history_roots: Vec[Int]; // root after append i+1
}

pub type ChainProof = {
  leaf_index: Int;
  leaf_count: Int;
  root: Int;
  siblings: Vec[Int];      // bottom level first
  directions: Vec[Int];    // 0 = sibling left, 1 = sibling right
}

pub type ChainThresholdGate = {
  threshold: Int;          // m
  member_count: Int;       // n
  approvals: Vec[Int];     // approved members in approval order
  executed: Bool;
  execution_nonce: Int;    // 0 before execution
  executed_at: Int;        // -1 before execution
  approvals_digest: Int;   // -1 before execution
}

pub type ChainExecutionReceipt = {
  nonce: Int;
  approval_count: Int;
  executed_at: Int;
  approvals_digest: Int;
}

pub type ChainCommitReveal = {
  commit_hash: Int;
  commit_tick: Int;
  reveal_tick: Int;
  expiry_tick: Int;
  revealed: Bool;
  revealed_value: Int;     // -1 until revealed
  reveal_at: Int;          // -1 until revealed
  refunded: Bool;
  refund_at: Int;          // -1 until refunded
}
```

Invariants produced by this module:

- Accumulator: `history_counts.len() == history_roots.len() == leaf_count`;
  `level_sizes.len() == level_starts.len()` and `level_sizes[0] ==
  leaf_count`; the last level has one node; for non-empty accumulators
  `root == levels[levels.len() - 1]`. Empty: all vectors empty,
  `leaf_count == 0`, `root == -1`.
- Proof: `siblings.len() == directions.len()` and
  `proof.leaf_count == acc.leaf_count`, `proof.root == acc.root` when
  generated by `chaincrypto_accumulator_proof`.
- Gate: `1 <= threshold <= member_count`, `approvals` holds distinct member
  indices in `0..member_count - 1`; `executed == true` implies
  `approvals.len() >= threshold`.
- Commit-reveal: `0 <= commit_tick < reveal_tick < expiry_tick`;
  `revealed` and `refunded` are never both true.

## 4. Hash model and node combine

A valid opaque hash is an `Int` in `0..2147483646` (2^31 - 2). The module
validates every hash it consumes and rejects out-of-range values with `Err`.

Internal nodes are built with the exported mix:

```
chaincrypto_node_combine(l, r) = (l + 31 * r + 7) % 2147483647
```

This is deterministic, commutative-free (`combine(l, r) != combine(r, l)`
whenever `l != r` and both are valid, because 2147483647 is prime and 30 is
invertible), and always returns a value in `0..2147483646`. It is opaque
booking, not security: callers wanting real commitments hash off-module and
feed the results in as leaves.

The root of the empty accumulator is `-1` (`chaincrypto_empty_root()`), a
sentinel outside the valid hash range, so it cannot collide with any real
root. Appending never produces `-1`.

## 5. Accumulator and root history

`chaincrypto_accumulator_new()` returns the empty accumulator.

`chaincrypto_accumulator_append(acc, leaf_hash)` validates `leaf_hash`,
copies the leaf vector, appends, rebuilds the level table and returns a new
accumulator. Rebuild is bottom-up with odd-node **promotion** (the same
shape family as `xiom.merkle`):

- level 0 is the leaves in append order;
- to reduce a level with `count > 1` nodes: pair `(0,1)`, `(2,3)`, ... as
  `combine(left, right)`; if `count` is odd the lone last node is copied to
  the next level unchanged (never duplicated); repeat until one node
  remains.

Every append also pushes `(leaf_count, root)` onto the root history, so
`history_root(i)` is the root of the prefix of `i + 1` leaves. History
accessors are bounds-checked.

Pinned roots over the fixture leaves `1000 + 37*i` (`i = 0..7`):

| leaves n | root |
|---|---|
| 0 | `-1` |
| 1 | `1000` |
| 2 | `33154` |
| 3 | `66455` |
| 4 | `1134343` |
| 5 | `1169938` |
| 6 | `2308940` |
| 7 | `3483499` |
| 8 | `40997095` |

The values were computed with an independent implementation of the same
combine/promotion rules and are pinned in `tests/test_conformance.xi`.

## 6. Membership proofs

### Format

`ChainProof` carries `leaf_index`, the source `leaf_count`, the source
`root`, `siblings` (values, bottom level first) and `directions`
(parallel; `0` = sibling on the left, `1` = sibling on the right).

### Generation

`chaincrypto_accumulator_proof(acc, leaf_index)` walks from level 0 to the
level below the root with a running index `idx` (starts at `leaf_index`) and
level size `size`:

- `idx` odd: the node is a right child; record the node at `idx - 1` with
  direction `0`;
- `idx` even and `idx + 1 < size`: the node is a left child with a right
  sibling; record the node at `idx + 1` with direction `1`;
- otherwise the node is promoted at this level and records nothing.

Then `idx = idx / 2`, `size = ceil(size / 2)`. Sibling counts therefore vary
with the leaf index; for a 7-leaf accumulator they are
`[3, 3, 3, 3, 3, 3, 2]`.

### Verification

`chaincrypto_proof_verify(proof, leaf_hash, root)` performs, in order:

1. Structural `Err`s (section 9): `leaf_count > 0`;
   `0 <= leaf_index < leaf_count`; `siblings.len() == directions.len()`;
   every direction is `0` or `1`.
2. `Err` when `leaf_hash` is not a valid hash. A `root` that is not a valid
   hash returns `Ok(false)` (it simply cannot match; `-1` included).
3. Fold with `h = leaf_hash`, `idx = leaf_index`, `size = leaf_count`,
   `consumed = 0`; while `size > 1`:
   - if the shape says the node has a sibling (`idx` odd, or `idx` even and
     `idx + 1 < size`): if no sibling remains (`consumed >= siblings.len()`)
     return `Ok(false)`; otherwise take `s = siblings[consumed]` and
     `d = directions[consumed]`, set
     `h = combine(h, s)` when `d == 1`, else `h = combine(s, h)`, and
     `consumed = consumed + 1`;
   - promoted level: consume nothing;
   - `idx = idx / 2`, `size = ceil(size / 2)`.
4. If `consumed != siblings.len()`, return `Ok(false)` (wrong proof length
   for this shape).
5. Return `Ok(h == root)`.

Because `combine` is not commutative, a flipped direction bit changes the
folded value and is rejected as `Ok(false)`. Rejection summary:

| Tampering | Result |
|---|---|
| wrong leaf hash | `Ok(false)` |
| wrong root | `Ok(false)` |
| tampered sibling value | `Ok(false)` |
| flipped direction bit | `Ok(false)` |
| reordered or truncated siblings (with matching directions) | `Ok(false)` |
| extra siblings | `Ok(false)` |
| direction outside `0/1` | `Err` |
| sibling/direction length mismatch | `Err` |
| `leaf_count <= 0` or `leaf_index` out of range | `Err` |
| leaf hash out of range | `Err` |

## 7. Threshold gate (m-of-n)

`chaincrypto_threshold_new(m, n)` requires `m >= 1`, `n >= 1`, `m <= n`.
Fresh gates have no approvals, `executed == false`, `execution_nonce == 0`,
`executed_at == -1`, `approvals_digest == -1`.

`chaincrypto_threshold_approve(gate, member)`:

- `Err` if `gate.executed`;
- `Err` if `member` is outside `0..member_count - 1`;
- `Err` if the member already approved (duplicate rejection);
- otherwise returns a new gate with the member appended to `approvals`.

`chaincrypto_threshold_met` is `approvals.len() >= threshold`.

`chaincrypto_threshold_execute(gate, now, nonce)`:

- `Err` if `gate.executed` (replay);
- `Err` if `nonce != execution_nonce + 1` (stale or skipped nonce = replay);
- `Err` if `approvals.len() < threshold`;
- otherwise returns a new gate with `executed == true`,
  `execution_nonce == nonce`, `executed_at == now` and
  `approvals_digest = fold(approvals)` where
  `fold(v)` starts at `0` and repeatedly `d = combine(d, v[i])`.

`chaincrypto_threshold_receipt(gate)` returns `Err` until the gate has
executed; afterwards it reports `nonce`, `approval_count`, `executed_at` and
`approvals_digest`. The digest is opaque (it folds approved member ids; it
is not a hash and not order-unique).

Execution is single-shot: the returned executed gate refuses further
approvals and further executions.

## 8. Commit-reveal

`chaincrypto_commit_reveal_new(hash, commit_tick, reveal_tick, expiry_tick)`
requires a valid `hash`, `commit_tick >= 0`, `reveal_tick > commit_tick`
and `expiry_tick > reveal_tick`. The reveal window is
`[reveal_tick, expiry_tick)`.

Phases (`chaincrypto_commit_reveal_phase(cr, now)`):

| Condition | Phase | Code |
|---|---|---|
| `now < reveal_tick` | waiting | `0` |
| `reveal_tick <= now < expiry_tick` | reveal | `1` |
| `now >= expiry_tick` | expired | `2` |

`chaincrypto_commit_reveal_reveal(cr, now, value)` checks, in order:

1. `Err` if `cr.revealed` (replay);
2. `Err` if `cr.refunded`;
3. `Err` if `now < reveal_tick` (waiting);
4. `Err` if `now >= expiry_tick` (expired);
5. `Err` if `value != cr.commit_hash`;
6. otherwise returns a new record with `revealed == true`,
   `revealed_value == value`, `reveal_at == now`.

The equality check in step 5 is the caller-supplied-hash boundary: the
caller reveals the preimage off-module and passes the opaque value; matching
it against the commitment is the whole check this module can make.

`chaincrypto_commit_reveal_refund(cr, now)` checks:

1. `Err` if `cr.refunded` (replay);
2. `Err` if `cr.revealed`;
3. `Err` if `now < expiry_tick`;
4. otherwise returns a new record with `refunded == true`,
   `refund_at == now`.

A refunded commitment can no longer be revealed; a revealed commitment can
no longer be refunded.

## 9. Error catalog

## 10. Complexity

| Operation | Complexity |
|---|---|
| `chaincrypto_node_combine` | O(1) |
| `chaincrypto_accumulator_append` | O(n) combines for n leaves (full rebuild) |
| accumulator accessors / record / history | O(1) |
| `chaincrypto_accumulator_proof` | O(level_count) = O(log n) |
| `chaincrypto_proof_verify` | O(log n) combines |
| proof accessors | O(1) |
| `chaincrypto_threshold_new` / `_met` | O(1) |
| `chaincrypto_threshold_is_approved` / `_approve` / `_execute` | O(approvals) |
| commit-reveal functions | O(1) |

The accumulator rebuilds all levels per append; this is deliberate for
clarity at conformance scale. A production port would keep a frontier.

## 11. Test plan

`tests/test_conformance.xi` (`module chaincrypto_tests`, 19 named tests,
hello-style printer returning the failure count). Fixture leaves are
`1000 + 37*i`; commit-reveal tests use ticks `(0, 10, 20)`. Coverage:

1. node mix determinism, order sensitivity (`combine(1,2)=70`,
   `combine(2,1)=40`), range errors, empty root `-1`;
2. empty accumulator: counts, record, no history, proof/accessor errors;
3. append: range errors, root vs. independent recomputation, history
   records, leaf and history bounds;
4. pinned roots for sizes 0..8 (table in section 5);
5. membership proofs round-trip for all 7 leaves, counts `[3,3,3,3,3,3,2]`,
   accessor fields;
6. rejection: tampered leaf, root, sibling, flipped direction, truncated and
   stretched proofs, wrong declared index, invalid root -> `Ok(false)`;
   invalid leaf hash, direction `2`, length mismatch -> `Err`;
7. structural proof errors for `leaf_count <= 0`, index bounds, missing
   siblings;
8. proof accessors against independently recomputed node values
   (`siblings` of leaf 0 and leaf 6 in the 7-leaf shape);
9. threshold construction errors and fresh-gate fields;
10. duplicate approval, out-of-range member, approval order, met gate;
11. execution gate: below threshold, nonce replay, success, second execution
    replay, approval after execution, receipt fields and digest `76`;
12. commit-reveal construction errors and fresh fields;
13. phase boundaries at ticks 0/9/10/19/20/999;
14. reveal waiting, value mismatch, success, replay, at/after expiry;
15. refund before expiry, success at expiry, replay, reveal after refund,
    refund after reveal;
16. determinism across identical builds, history prefix consistency, leaf

17. shapes 1..8 invariants plus promoted-leaf sibling counts (5/3/6 leaves);
18. pinned error-catalog messages;

## 12. Compiler notes (v0.62.2)

- Free functions only; no methods, no lambdas, no `Vec[fn]` dispatch, no
  `Vec[StructType]`. Struct vector fields are copied explicitly with
  `&mut` append helpers and mirror-pushed in lockstep.
- `Ok`/`Err` are constructed only in the per-type leaf helpers
  (`_cc_ok_*` / `_cc_err_*`); public code returns through those helpers.
- Every loop makes progress and terminates; the suite runs in well under a
  second on the pinned toolchain.
- No `Vec[Str].push` anywhere (mis-lowered on this compiler); no FFI
  declarations; module-level state is absent.
- The module imports only `xiom.convert` (for `int_to_string` in error
  messages); it needs no string builder and no byte buffers.
